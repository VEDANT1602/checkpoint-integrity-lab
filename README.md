# Checkpoint Integrity Lab

**A checkpoint is useful only when it represents a complete training state you can actually resume.**

I built this independent CPU experiment to separate a saved weight file from a recoverable training trajectory. A small PyTorch network trains with Adam, dropout and randomized minibatches. The run then compares continuous training with full-state recovery and two incomplete restore strategies.

## The failure I wanted to expose

Selecting the newest checkpoint directory assumes that it was fully published and that its payload still matches its manifest. Restoring only model weights assumes that optimizer moments and random-number state do not affect the next update. Both assumptions are testable without a GPU cluster.

My framework is **capture → publish → verify → select → resume**. A checkpoint contains model state, optimizer state, step, architecture and CPU Torch RNG state. The writer atomically replaces individual files, then publishes a completion marker bound to the manifest. The reader checks completeness, file length, hashes, schema, architecture, tensor validity and state compatibility before considering a candidate usable.

## What I ran

The original dataset has 256 fictional six-feature examples. A `6→16→2` network, dropout 0.2 and Adam train for 40 steps with 64-example randomized minibatches. The experiment creates:

- A complete step 12 checkpoint.
- A newer step 20 checkpoint whose payload is truncated after publication.
- A step 28 payload whose manifest and completion marker are never published.

The reader rejects the two newer candidates and resumes step 12. All comparisons use the same model, data, step count and CPU environment.

| Restore strategy | Maximum parameter difference from continuous training |
|---|---:|
| Model + optimizer + CPU RNG | 0.000000 |
| Model weights only | 0.405736 |
| Model + optimizer, without RNG | 0.261498 |

The full-state loss trajectory also matches exactly in the recorded PyTorch 2.9.1 CPU run. These are **parameter-parity measurements**, not task accuracy. The [raw metrics](results/metrics.json), [loss curves](results/loss-curves.csv), [complete step 12 state](models/complete-step12.pt) and [resumed model](models/resumed-model.pt) are included.

## Reproduce

Python 3.11, CPU, no model downloads or paid service:

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python run.py --output runs/local
```

`run.py` creates its fault candidates in a temporary directory and preserves the valid model artifacts plus the rejection trace. [lab.py](lab.py) implements checkpoint publication and loading. [Tests](tests/test_checkpoint.py) cover resume parity, corrupted/incomplete candidate fallback, marker binding, no-valid-state refusal, nonfinite optimizer state, create-only snapshots and artifact commitments. Only files generated by this project are loaded, using `weights_only=True` and CPU mapping.

## The decision and its limit

My recommendation is to make a checkpoint's completeness contract explicit and preserve every state component required by the chosen training loop. A directory timestamp or a loadable weight file is insufficient evidence of trajectory recovery.

The experiment is deterministic, single-process and same-version on CPU. It simulates publication faults through orderly local operations; it does not kill a process or test power loss, filesystem durability, multi-host coordination, Ray, FSDP or GPU recovery. Hashes establish identity relative to the supplied manifest, not authenticity against a hostile writer. Local checkpoint directories and adapters are trusted; `weights_only=True` is a deserialization restriction, not a complete hostile-file sandbox.

Next I would inject actual process termination, test another filesystem, and then add distributed rank/state reconciliation. Those experiments need their own evidence before any distributed-recovery claim.
